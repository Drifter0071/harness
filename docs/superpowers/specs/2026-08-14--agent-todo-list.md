# Agent Todo List — Spec

> **Status:** Draft, awaiting review.
> **Date:** 2026-08-14
> **Author:** Mavis (brainstorming session with gellert)
> **Related:** `PRODUCT.md` (workspace + multi-agent loop), `DESIGN.md`
> (visual contract, glass-mist / glass-quartz, monochrome palette),
> `AGENTS.md` (code conventions).

## Goal

Give the main harness agent a first-class, session-scoped **todo list** that:

- The agent can author and update via native provider tool calls
  (`todo_set`, `todo_append`, `todo_update`, `todo_remove`, `todo_clear`).
- The user can see at a glance as a compact strip in the ChatHeader
  row, expanding into a `glass-mist` popover with inline edit
  affordances.
- Persists in the existing session file
  (`.harness/sessions/<id>.json`), no new persistence machinery.
- Enforces a "finished list" rule so the agent can only overwrite the
  plan once all items are done, preventing the agent from clobbering
  a live plan the user is still acting on.

The todo list is **the agent's plan, visible to the user, editable by
the user**. It is not a separate chat thread, not a project-level
roadmap, not a personal scratchpad. One list per session, hidden when
empty.

## Design

### 1. Data model

#### 1.1 Rust — `src-tauri/src/session.rs`

```rust
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum TodoStatus { Pending, InProgress, Done }

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct TodoItem {
    pub id: String,         // UUID v4, server-side generated
    pub text: String,       // 1..=280 chars, validated
    pub status: TodoStatus,
    pub order: u32,         // 0-based, sparse allowed (gaps on delete)
}

#[derive(Debug, Clone, Default, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct TodoList {
    pub items: Vec<TodoItem>,   // kept sorted by `order` on read
    pub version: u32,           // bumped on every commit; matches
                                // Session::version's type
}

// Existing `Session` struct gains:
pub struct Session {
    // ...existing fields...
    #[serde(default)]
    pub todos: TodoList,
}
```

`#[serde(default)]` on the new `todos` field means **old session files
load with an empty todo list**, no migration needed. Field types and
serde conventions match the surrounding code in `session.rs`
(`camelCase` everywhere; `u32` for `version` to match `Session::version`
at line 254).

#### 1.2 Frontend — `src/lib/store.ts`

```ts
export type TodoStatus = "pending" | "in_progress" | "done";

export interface TodoItem {
  id: string;       // UUID v4, generated by Rust
  text: string;
  status: TodoStatus;
  order: number;
}

export interface TodoList {
  items: TodoItem[];
  version: number;  // u32 from Rust, fits safely in JS number
}

// On the store:
todos: TodoList;
hydratedTodosFor: string | null;  // session id we hydrated for;
// used to skip re-hydration when the same session is re-loaded
setTodos(list: TodoList): void;
```

Rust generates all ids with `Uuid::new_v4().to_string()` (see
`agent_loop.rs:405, 472, 1248`, `session.rs:538`). The FE is
format-agnostic — the shared `id: string` works for either side.

### 2. Provider tool surface (`src-tauri/src/tools.rs`)

Five new tools, registered alongside existing workspace tools. All
return `TodoList` on success.

| Tool | Args | Effect | Action-mode |
|---|---|---|---|
| `todo_set` | `{ items: [{text, status?}] }` | Replace the whole list. Rejected if list is active (see §6). | Free |
| `todo_append` | `{ items: [{text, status?}], position? }` | Insert items at `position` (defaults to end). | Free |
| `todo_update` | `{ updates: [{id, text?, status?, order?}] }` | Patch specific items by id. | Free |
| `todo_remove` | `{ ids: string[] }` | Delete items by id. | Gated (Commands mode prompts) |
| `todo_clear` | `{}` | Wipe the list. | Gated (Commands mode prompts) |

The action-mode gate is the same one `run_command` uses today. The
gating lives in `requires_approval` in `agent_loop.rs:302-307`:

```rust
fn requires_approval(mode: &CommandMode, name: &str) -> bool {
    match mode {
        CommandMode::Commands => {
            name == "run_command"
                || name == "todo_remove"
                || name == "todo_clear"
        }
        CommandMode::Yolo => false,
    }
}
```

So `todo_remove` and `todo_clear` flow through the same `agent-approval-request`
event / FE approval card path as `run_command`. The other three are
unconditional — they only mutate session state the user already owns.

Tool-call JSON schemas follow the same shape as existing tools. Each
item text enforces `minLength: 1, maxLength: 280`.

### 3. IPC commands (`src/lib/ipc.ts`, `src-tauri/src/commands.rs`)

User-initiated edits. No approval gate — these are direct human
actions, the agent will see the new state on its next turn.

| Command | Args | Returns |
|---|---|---|
| `edit_todo` | `{ project_path, session_id, id, text?, status?, order? }` | `TodoList` |
| `append_todo` | `{ project_path, session_id, items: [{text, status?}], position? }` | `TodoList` |
| `remove_todo` | `{ project_path, session_id, ids: string[] }` | `TodoList` |
| `clear_todo` | `{ project_path, session_id }` | `TodoList` |

`project_path` is required (every session-mutating command in
`commands.rs` carries it — `save_session` keys its writes by it).
The four commands are registered as Tauri `#[tauri::command]`s in
`commands.rs`, alongside `set_session_mode` / `set_session_model` /
etc.

All four go through the same `save_session` write path as the existing
mutators, bump `TodoList::version`, and emit the same `todo_changed`
event.

### 4. Streaming event

A new event on the existing Tauri event bus:

```
todo_changed {
  session_id: string,
  list: TodoList,
  source: "agent" | "user"
}
```

Emitted after every commit. The `source` field lets the frontend
choose to flash a subtle highlight on agent mutations while leaving
user edits visually quiet (user edits are already obvious from the
interaction).

### 5. Concurrency

There is no global `Mutex<Session>` in the codebase — every session
mutator does `load_session` → mutate → `save_session` (see
`set_session_mode` at `commands.rs:418-428`). Two near-simultaneous
writes can both load-modify-save the same file and the second
silently overwrites the first.

We add a per-session serialization gate inside the four `todo_*` IPC
handlers and the `todo_*` tool handlers:

```rust
// Pseudo:
let _guard = session_write_lock(&project_path, &session_id).await;
// ... mutate ...
save_session(&project_path, &session).await?;
```

Implemented as `Arc<tokio::sync::Mutex<HashMap<(String, String), Arc<tokio::Mutex<()>>>>>`,
lazily inserting per-(project, session) entries. The guard is
released when `_guard` drops. The agent loop holds no per-session
lock long-term — only the actual mutate-and-save window.

The `TodoList::version` field is the logical clock: every commit
increments it by 1, regardless of source. The FE uses it on
incoming `todo_changed` events to detect lost optimistic updates:
if the incoming `version` is greater than the local optimistic
version, the local state is replaced. (Same-session race is now
serialized by the lock above, so the FE's version comparison is a
belt-and-suspenders check, not a hard correctness requirement.)

### 6. Frontend components

#### 6.1 `src/components/PlanStrip.tsx` (new)

The hairline anchor strip. Lives in `ChatHeader` (the row directly
under the title bar), rendered as a second centered line below the
existing model/tokens/usage row, before the cumulative/session-window
row. The current `ChatHeader` is a single centered cluster
(`flex items-center justify-center gap-3`); we keep that cluster
intact and add the strip as its own horizontal row beneath it,
matching the existing two-row rhythm (cluster + progress bar on
row 1; cumulative + session window on row 2).

- **Hidden when** `items.length === 0`. Mounted always (zero-cost
  render). The first `todo_changed` event with non-empty items makes
  it appear.
- **Rest visual:** `glass-mist` pill, `--m-radius: 999px`,
  `text-[11px] text-white-50 font-medium gap-1.5`.
- **Content (rest):** `Plan` wordmark (section-label recipe:
  `text-[9px] uppercase tracking-[0.14em] text-white-15`) + progress
  fraction `n/m` in `text-white` + `next: <next pending text>` in
  `text-white-30` + chevron (`ChevronDown`, 12px, rotates 180° when
  `data-open="true"`).
- **"All done" transition:** strip text changes to `Plan · done` in
  `text-status-active` for 1.2s, then settles to plain `Plan`. The
  `status.active` left rule (2px) appears on the popover header during
  this window. The transition only fires on the *transition* from
  non-finished to finished; loading a session that was already
  finished does not re-trigger it.
- **Drag region:** the strip is in the ChatHeader row, outside the
  title bar's `data-tauri-drag-region` strip — no opt-out needed.

#### 6.2 `src/components/PlanPopover.tsx` (new)

The hover/focus surface. Portaled to `<body>` at `z-[85]` (just under
Bip's thought popover at `z-[90]`). Anchored 12px below the strip.
Width 320px, max-height 360px (internal scroll for >10 items).

Uses the same shared-hover state trick as Bip's thought popover so
the 8px gap doesn't close it mid-read. Click outside closes. `Esc`
closes. Click inside doesn't close.

**Structure (top → bottom):**

1. **Header row.** `Plan` label (section-label recipe) on the left,
   `n/m done` count on the right. `text-[11px] text-white-30`,
   `px-3 py-2 border-b border-border-subtle`.
2. **Items list.** `flex flex-col gap-px`, each row 32px tall,
   `px-3 hover:bg-white/[0.04]`:
   - **Status pill (24×24 left):** clickable, cycles
     `pending → in_progress → done → pending` on click. `rounded-full
     border`. Pending = `bg-surface-2 border-border`. In progress =
     `bg-status-active/15 border-status-active` with `animate-pulse`.
     Done = `bg-status-active border-status-active` with a `Check`
     Lucide (12px) inside. Click dispatches `edit_todo` with the new
     status.
   - **Text.** `text-[13px]`. `text-white` when pending or
     in_progress; `text-white-30 line-through` when done. Click →
     `contenteditable`. `Enter` commits, `Esc` reverts, blur
     commits. The 280-char cap is enforced server-side; the FE
     applies the same limit in an `onBeforeInput` handler that
     prevents insertion past the cap (not `maxLength`, which only
     works on `<input>` / `<textarea>`). Empty text on commit is
     treated as delete.
   - **Hover affordances (right side, fade in on row hover, 100ms):**
     `GripVertical` (12px, `text-white-30 cursor-grab`) and `X` (12px,
     `text-white-30 hover:text-status-error`).
3. **`+ Add step` row** at the bottom. `Plus` icon (12px) + `text-white-30
   text-[12px]`. Click → inline input (same recipe as item text),
   `Enter` commits via `append_todo`. The `+` row also serves as the
   drop target for the end of the list when dragging.
4. **Footer.** `Clear plan` button on the right (`text-white-15
   text-[11px]`, hover `text-status-error`). Dispatches `clear_todo`.

**Drag-reorder.** Native HTML5 drag (`draggable`, `onDragStart`,
`onDragOver`, `onDrop`). On drop we compute new sparse `order` values
as `step * 1000` so future inserts between items don't require
re-numbering the whole list. One `edit_todo` per affected item,
batched in a single IPC call (the FE coalesces contiguous moves into
one round-trip).

**Animation budget.** Strip fade-in: 150ms. Popover open: 100ms
`translate-y-1 → 0`. All animations respect `prefers-reduced-motion`
(zero-out transforms).

Pure helpers, no React. Selectors and derived state:

#### 6.4 Store wiring (`src/lib/store.ts`)

- `setTodos(list)` — replace the slice. Called on session hydrate
  (`useProjectLifecycle`) and on every `todo_changed` event.
- Optimistic update path: when a user edit dispatches, the FE
  immediately applies the change to the store, then reconciles when
  the `todo_changed` event arrives. If the incoming `version` is
  greater than the local optimistic version, the local state is
  replaced. The hydration call goes in the same
  `useStore.setState({...})` batch as `messages` / `activities` /
  `toolCalls` (see `applySession` at `session-manager.ts:226-239`)
  to avoid a separate re-render.

### 7. The "finished" rule (list-level overwrite permission)

The list is `finished` when `items.length > 0 && items.every(i =>
i.status === Done)`. This is **derived state**, not stored — the
frontend computes it from the items, the Rust validator computes it
the same way.

**Validator (in `todo_set` handler):**

```rust
fn validate_todo_set(session: &Session, new_items: &[TodoItem]) -> Result<(), ToolError> {
    let current = &session.todos.items;
    let is_empty = current.is_empty();
    let is_finished = !current.is_empty()
        && current.iter().all(|i| i.status == TodoStatus::Done);

    if !is_empty && !is_finished {
        return Err(ToolError::Rejected(
            "Cannot overwrite an active todo list. Finish all items or use \
             todo_append / todo_update to modify the current list.".into()
        ));
    }
    Ok(())
}
```

This is a **soft enforcement** — the agent gets a clear error and a
hint, the LLM self-corrects. The user can always wipe via
`clear_todo` (or by manually checking off remaining items) to allow
overwrite.

### 8. Tool error shape

The agent loop's tool call path returns `Result<ToolResult, String>`
(see `tools.rs:444-463` and the wrapper at
`agent_loop.rs:1343-1350`). `ToolResult` is:

```rust
pub struct ToolResult {
    pub ok: bool,
    pub summary: String,
    pub content: Option<String>,
}
```

The validator's `ToolError::Rejected` is converted to
`ToolResult { ok: false, summary: <hint>, content: None }` before
being sent to the LLM. The LLM sees the hint as a normal tool result
and self-corrects on its next round.

### 9. System prompt addition (`src-tauri/src/agent.rs`)

A short paragraph appended to `ORCHESTRATOR_PROMPT` (the existing
system-prompt constant at `agent.rs:12-18`):

```
## Plan (todos)

You have a session-scoped todo list visible to the user at the top of
the chat as a compact menu. Use it to plan non-trivial multi-step work
so the user can see what's coming and edit it before you start.

Rules:
- At the start of any non-trivial task, call `todo_append` (or
  `todo_set` if the list is empty) to publish your plan.
- Update items as you work: `todo_update` to mark `in_progress` when
  you start, `done` when you finish. Don't batch — update live.
- You may only call `todo_set` (replace the whole list) when the
  current list is empty or all items are `done`. The system will
  reject otherwise.
- Keep item text short and action-oriented ("Read the auth handler",
  not "We will now begin the process of reading..."). Max 280 chars.
- For trivial single-step requests, no plan is needed.
```

The full Orchestrator prompt is `ORCHESTRATOR_PROMPT` at `agent.rs:12`.
The paragraph above is appended to it as a single concatenated `&str`
at the call site, or moved into a `pub const ORCHESTRATOR_PROMPT: &str`
re-declaration — implementer's choice; spec only requires the
content.

### 10. Context for the LLM (every turn)

The current todo list is included in the message context the LLM
sees, formatted as a compact block before the conversation. The
context assembly happens inside `run_agent_turn` in
`agent_loop.rs`; we extend the existing context-injection step (next
to the active-model and session-metadata blocks — wherever the
`tokenStats` and `activeModel` are already folded into the request)
to add a `[Plan: n/m done]` block as shown:

```
[Plan: 2/5 done]
  ✓ Read the auth handler
  ✓ Inspect the token refresh path
  → Add retry logic to the refresh call
  ⏵ Add telemetry around failed refreshes
  ⏵ Write a test for the new retry branch
```

Implementation note: this is appended to the **system message** the
LLM sees (not the user message), so it stays stable across
multi-turn flows and isn't treated as fresh user input.

### 11. Chat breadcrumb

A small toast/badge in the chat area on every `todo_changed` event
("Plan updated: 3 items"). Reuses the existing `showToast` host
(already in `App.tsx`) — a 2-3 second toast at the bottom-right.
This is the same notification surface used for "Settings saved" /
"Model added" etc., so the visual stays consistent.

### 12. Persistence

No new files. `Session` serializes/deserializes the new `todos` field
through the existing flush. Writes go through `save_session`; the
session-watcher's `session-file-changed` event re-emits to the FE so
the store can re-hydrate. The debounce that coalesces writes is on
the TS side (`session-manager.ts`'s `scheduleSave`).

### 13. Error handling

| Failure | Behavior |
|---|---|
| Agent calls `todo_set` on an active list | Tool returns `ToolResult { ok: false, summary: <hint> }`. The LLM sees the hint as a tool result and self-corrects. |
| `edit_todo` IPC fails (session file lock, deserialization) | Frontend rolls back the optimistic update and surfaces a toast. Strip/popover revert to the last-known-good state. |
| Item id doesn't exist in `todo_update` / `todo_remove` | `ToolResult { ok: false, summary: "unknown item id" }`. Agent retries with correct ids. |
| `text` empty after editing | Treated as delete. FE enforces via `contenteditable` commit logic. |
| `text` over 280 chars | Validator rejects, error names the limit. FE `onBeforeInput` blocks the insertion. |
| Concurrent agent + user edits to the same item | Per-session write lock in the Rust handlers (§5). `version` is bumped on every commit. FE compares version on incoming `todo_changed`; older local optimistic state is replaced. |
| Session file fails to parse (corrupt JSON, pre-todo schema) | `#[serde(default)]` on `todos` means old sessions load with an empty list. No migration. |
| `npm run dev` browser mode | Event bus registration is swallowed (`.catch(() => {})`, per `session-manager.ts:80-83`). Strip stays at its last known state. User-initiated IPC edits still work for the lifetime of the page (they go through Tauri command invocation, not the event bus). The agent never runs in the browser anyway. |

### 14. Edge cases

- **Empty list + `todo_set({items: []})`.** Allowed (clears the list).
- **`todo_append` with `position` past end.** Treated as "append at
  end". No error.
- **User drags an item to its current position.** No-op, no IPC.
- **Popover open + user types in chat composer.** Popover stays open,
  no focus stealing.
- **User mid-rename + `todo_changed` arrives.** Cancels the
  contenteditable, replaces local state, unsaved text lost.
  Acceptable for v1.
- **Long lists (>20 items).** Popover max-height 360px, internal
  scroll, fixed 32px row height. Drag works within the scroll
  container.
- **`isFinished` highlight only fires when transitioning from
  non-finished to finished** (not on session load of a pre-existing
  finished list — see §6.1).
- **`isFinished` is true but list is empty.** Treat as not-finished
  for overwrite purposes (current validator's `is_finished` check
  already requires `!is_empty`).

## Out of scope (v1)

- Conflict-resolution UI (last-write-wins is enough for v1).
- Per-turn todo history / "what was the plan at step 3?" replay.
- Project-level (workspace-scoped) todo lists.
- Personal human-only scratchpad mode.
- Sub-agent todos — the orchestrator can dispatch sub-agents and
  each sub-agent has its own plan in its own session tile, but the
  parent todo list does not auto-decompose.
- Todo templates or recurring plans.
- Drag-to-reorder across sessions (would need a different storage
  model).
